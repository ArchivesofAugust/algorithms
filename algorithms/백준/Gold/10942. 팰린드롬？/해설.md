# 10942. 팰린드롬? — 해설

## 핵심 아이디어

M(최대 100만) 번의 구간 팰린드롬 질문마다 매번 O(N) 투 포인터로 확인하면 O(NM) = 최악 20억 번 연산이라 시간 초과. 대신 **모든 구간 [i, j]의 팰린드롬 여부를 미리 DP로 전처리**해두면 질문마다 O(1) 조회로 끝난다.

## 접근 방법

`dp[i][j]` = `a[i..j]`가 팰린드롬인지 여부.

- 길이 1: `dp[i][i] = true` (항상 팰린드롬)
- 길이 2: `dp[i][i+1] = (a[i] == a[i+1])`
- 길이 3 이상: `dp[i][j] = (a[i] == a[j]) && dp[i+1][j-1]`
  - 양 끝이 같고, 그 안쪽 구간도 팰린드롬이어야 전체가 팰린드롬

이건 10988에서 쓴 투 포인터 판별("양 끝 비교하며 안쪽으로")을 **모든 구간에 대해 한 번에 계산**하도록 DP로 확장한 것 — `dp[i+1][j-1]`이 "안쪽으로 한 칸씩 좁혀가는" 투 포인터 재귀 관계 그 자체다.

길이(`len`)를 2부터가 아니라 짧은 구간부터 오름차순으로 채워야 하는 이유: `dp[i][j]`를 계산하려면 그보다 안쪽의 더 짧은 구간 `dp[i+1][j-1]`이 먼저 계산되어 있어야 하기 때문 (전형적인 구간 DP의 반복 순서).

## 시간/공간 복잡도

- 전처리: 시간 O(N²), 공간 O(N²) — N ≤ 2000이므로 최대 400만 칸, boolean 배열로 감당 가능
- 질문당: O(1)
- 전체: O(N² + M)

## 헷갈렸던 점 / 주의할 점

- M이 최대 100만이라 입력 속도가 병목이 될 수 있다 — `Scanner` 대신 `BufferedReader`/`StreamTokenizer`로 읽고, 출력도 `System.out.println`을 매번 호출하지 말고 `StringBuilder`에 모아 한 번에 출력해야 한다.
- 길이 2 케이스(`dp[i][i+1]`)를 별도로 처리하지 않고 길이 3 이상 점화식에 억지로 끼워 넣으려 하면 `dp[i+1][j-1]`에서 `i+1 > j-1`이 되는 인덱스 문제가 생긴다 — 길이 1, 2는 base case로 분리.
- 10988(단일 문자열 O(N) 판별) → 10942(모든 구간을 O(N²)로 미리 계산해 O(1) 질문 응답)로 이어지는 "판별의 확장"이 이 시리즈의 핵심 전환점.
